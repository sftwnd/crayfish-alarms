Alarms for Java, on time and in order

A time range keeps elements until their moments and gives out those that have come, in the order of their moments. A service fires them in one thread, waits for the nearest one without a busy loop, and takes new ones from any thread — 1,600,000 alarms per second in one process.

Install

The library is on Maven Central. crayfish-alarms-service brings crayfish-alarms-timerange with it; a range without the service needs the time range only.

<dependency>
    <groupId>com.github.sftwnd.crayfish.alarms</groupId>
    <artifactId>crayfish-alarms-service</artifactId>
    <version>1.1.0</version>
</dependency>
implementation 'com.github.sftwnd.crayfish.alarms:crayfish-alarms-service:1.1.0'
implementation("com.github.sftwnd.crayfish.alarms:crayfish-alarms-service:1.1.0")

On Java 9+ the jars are the named modules com.github.sftwnd.crayfish_alarms_timerange and com.github.sftwnd.crayfish_alarms_service; they are OSGi bundles too. Use the same version of both. The only dependency is crayfish-common-expectation.

What it does

Reminders, deadlines, timeouts, scheduled deliveries: many elements, each with a moment, fired when the moment comes — without a timer task per element.

  • A bounded period of time

    A range accepts the elements of its period, from its start to its end, and returns the others as rejected. It is complete once it is empty after its end and its completeTimeout.

  • In order, each once

    An extraction gives out the elements whose moments have come, in the order of their moments, then of the comparator. A duplicate of a waiting element of its moment is not added.

  • Any time marker

    An Instant or any TemporalAccessor, an element that knows its moment (Expected), any element with a function that gives its moment, or transformers of your own.

  • One thread, any producer

    The service runs the range in the thread of process. addElements works from any thread and returns a stage that completes with the rejected elements.

  • Virtual threads

    The process waits on a ReentrantLock and its Condition: a virtual thread that runs it leaves its carrier while it waits, on JDK 21 to 23 as well.

  • Wake-ups on the grid

    The process wakes up on the grid of the clock: a millisecond by default, precise waits with a step of zero, or a coarser step for fewer wake-ups and more alarms per extraction.

  • Compact

    A chunk of the range keeps the moments in a long[] and the elements in an Object[]: 36 bytes per Instant, the Instant included, against 92 in 1.0.5.

  • No stop for a big chunk

    A chunk with 4,096 elements or more is split into parts of its interval, and an extraction sorts the parts that fire: 0.08 ms for the first extraction of a chunk of 400,000 elements.

  • Consistent on failure

    An exception of the comparator or of the reducer takes nothing out of the range. The process ends with it, and the range keeps its alarms for the next one.

  • Java 8+ and modular

    Java 8 bytecode; on Java 9+ named JPMS modules of multi-release jars, with OSGi bundle headers. Two builds of the same sources give the same jars byte for byte.

Tested. On JDK 8, 11, 17, 21 and 25: random operations against a model of the contract, every comparison of a script failing in turn, splits against a model, a series of 10,000 registrations for the lost wake-up, and a virtual thread that has to leave the only carrier.

In code

A factory, a range and a service. The examples compile against 1.1.0; the README explains every parameter.

A range of an hour in chunks of a second. It is not thread-safe: one thread adds and extracts, or the service does. More

ITimeRange<Reminder, Reminder> range = ITimeRangeFactory.<Reminder, Instant>packable(
        Duration.ofHours(1), Duration.ofSeconds(1), Duration.ofSeconds(30),
        Reminder::getDue, Comparator.comparing(Reminder::getId)
).timeRange(Instant.now());

Collection<Reminder> rejected = range.addElements(reminders);           // out of the hour: returned
Duration wait = range.duration(Instant.now());                          // until the nearest reminder
Collection<Reminder> due = range.extractFiredElements(Instant.now());   // the ones that have come, in order
boolean done = range.isComplete();                                      // past the end, and empty

The consumer gets the fired elements in the thread of the process, and so does an action of the stage of a request without an asynchronous method. More

AlarmTimeRangeService<Reminder, Reminder> service = new AlarmTimeRangeService<>(range, null);
Thread process = new Thread(() -> service.process(fired -> fired.forEach(this::notify)));
process.start();

// producers in any thread; an action that takes time goes to an asynchronous stage
service.addElements(batch).thenAcceptAsync(rejected -> rejected.forEach(this::tooLate));

process.interrupt();   // stops the process; it also ends after the range and its completeTimeout

An element that knows its moment, or any element with a function that gives it. More

class Alarm implements Expected<Instant> {   // getTick() is its moment
    ...
}
ITimeRange<Alarm, Alarm> alarms = ITimeRangeFactory.<Alarm>expected(
        Duration.ofMinutes(5), Duration.ofSeconds(1), Duration.ofSeconds(10),
        Comparator.comparing(Alarm::getId)
).timeRange(Instant.now());

// any element with a function that gives its moment, here an ISO-8601 string
ITimeRange<String, String> strings = ITimeRangeFactory.<String, Instant>packable(
        Duration.ofSeconds(10), Duration.ofSeconds(1), Duration.ofSeconds(3),
        Instant::parse, String::compareTo
).timeRange(Instant.now());

The step of a wake-up, the busy loop of minimalWait, and alarms fired ahead of their moments. More

// the default: wake-ups on the grid of a millisecond of the clock
AlarmTimeRangeService<Instant, Instant> byDefault = new AlarmTimeRangeService<>(range, null);
// precise waits: closer to the moments, at up to 2–3.5 times the CPU
AlarmTimeRangeService<Instant, Instant> precise = new AlarmTimeRangeService<>(range, null, Duration.ZERO);
// a wake-up every 10 ms at most: more alarms per extraction
AlarmTimeRangeService<Instant, Instant> coarse = new AlarmTimeRangeService<>(range, null, Duration.ofMillis(10));
// a busy loop for the last 200 µs of a wait, at the cost of a core
AlarmTimeRangeService<Instant, Instant> spinning = new AlarmTimeRangeService<>(range, Duration.ofNanos(200_000), Duration.ZERO);

// fire every alarm 50 ms ahead of its moment
byDefault.process(fired -> fired.forEach(System.out::println), Duration.ofMillis(50));

On JDK 21+ the process can run in a virtual thread: it does not pin its carrier while it waits. More

// the process waits on a ReentrantLock: its carrier is free while it waits, on JDK 21 to 23 too
Thread process = Thread.ofVirtual().name("alarms").start(
        () -> service.process(fired -> fired.forEach(System.out::println)));

How the service works

One process thread owns the range; other threads only queue requests. The process sleeps until the next alarm or the next request, never in a busy loop by default.

  1. Register

    addElements queues a copy of the elements and wakes the process if it waits. The stage of the request completes with the elements out of the range.

    any thread

  2. Wait

    The process waits for the nearest moment, rounded to the grid of the step of a wake-up, or for a request. A virtual thread leaves its carrier.

    the process

  3. Extract

    The range gives out the elements whose moments have come, in order. Only the parts of a chunk that fire are sorted; nothing is taken out if a comparison fails.

    the process

  4. Consume

    The consumer gets the fired elements in the thread of the process. A long action delays the next alarms: hand it to an executor.

    the process
